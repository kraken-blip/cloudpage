## Для чего нужен CloudPage

Личный веб-кабинет Дмитрия для перехода в панели управления его серверами. Вход в CloudPage защищён отдельным логином администратора. В кабинете можно добавить сервер, выбрать страну или значок, ввести название, адрес веб-панели и описание. Кнопка перехода открывает сохранённый адрес. Пользователь вводит логин и пароль на самой целевой панели. CloudPage хранит карточки, а браузер открывает целевые панели напрямую. Предпочтительный дизайн — тёмный кабинет, бело-оранжевый логотип CloudPage и тот же значок на экране «Домой». Выбор страны в редакторе должен быть адаптивным и визуально совпадать с остальными полями.

## Установка и эксплуатация

На VPS скопировать по SFTP только `exports/cloudpage-install.run` в `/root` и запустить `bash /root/cloudpage-install.run`. Пункт 1 устанавливает CloudPage. Пункт 2 управляет зависимостями Docker. При работающем Docker Engine установщик использует его и запрашивает подтверждение только на установку недостающего Buildx или Compose v2, когда план APT добавляет один пакет. Пункт 5 продолжает прерванную установку или восстанавливает запуск. После установки команда `sudo cloudpage` открывает меню управления.

Данные CloudPage размещаются в `/opt/cloudpage`. Compose-проект называется `cloudpage`, сеть — `cloudpage_private`, образ — `cloudpage:local`. Веб-контейнер публикует локальный порт на `127.0.0.1`, по умолчанию 17840. Есть три варианта доступа: отдельный Caddy для публичного HTTPS, существующий HTTPS-прокси и SSH-туннель. Встроенный Caddy использует TCP 80 и выбранный публичный HTTPS-порт. Выбирайте свободные порты с учётом уже работающих служб.

Требование владельца проекта — CloudPage работает рядом с 3X-UI и AmneziaWG. Операции установки, восстановления, перезапуска и очистки должны быть ограничены CloudPage. Общий Docker Engine и чужие контейнеры, конфигурация, порты и данные требуют отдельной проверки и разрешения на изменение. Серверные команды по умолчанию выполняются в видимом Termius, когда пользователь поручил работу на VPS. Папка проекта не содержит доступ к VPS и не даёт разрешения на серверные изменения.

## Повторный запуск и данные

- До сборки проверяются Docker Engine, Buildx, Compose, место на разделе и выбранные порты. Если сборка оборвалась, пункт 5 повторит её. Если образ уже собран с меткой текущих исходников, он используется повторно. Образ с неподтверждённым происхождением под тем же тегом блокирует установку. Для старого подтверждённого неполного каталога с пустым `admin.json` предусмотрена отдельная ветвь.
- Конфигурация новой установки подготавливается во временной папке и переносится в рабочий каталог до запуска контейнеров. Если она уже записана, пункт 5 использует её и запускает проект с `--no-recreate`. Проверка ссылки отделена от запуска контейнеров.
- Карточки находятся в `/opt/cloudpage/data/services.yaml`, резервная копия последней записи — `services.yaml.bak` в том же каталоге. Для переезда карточек достаточно приватно перенести `services.yaml` на новую установку, предварительно сохранить её текущий список и выставить на файле владельца `1000:1000` и режим `0600`. Загрузка этого файла заменяет список целиком. Учётные данные CloudPage хранятся отдельно в `admin.json`; для простого переноса карточек он не нужен. В этой работе карточки не переносились.

## Сборка, проверка и точка продолжения

Из корня папки проекта запустите `python3 cloudpage/tools/package-cloudpage.py`. Скрипт проверяет состав и содержимое архива и синтаксис оболочки. На 18.11.2026 установка собиралась после переноса в эту папку, архив содержал 37 файлов. На имитации Docker и APT проверили повторное использование образа, отказ при занятом порте, запуск настроенного Compose-проекта с `--no-recreate`, отказ при чужом проекте, отдельную ошибку доступа к URL и добавление только Compose при допустимом плане APT. Для текущего установщика полноценный прогон на Linux VPS с реальными Docker/APT и публичным TLS не проводился. Пользователь сообщал о рабочей предыдущей установке, что не подтверждает состояние новой версии.

Следующая доработка определяется поручением пользователя. Если задача касается установки, полезная проверка — отдельный тестовый Linux с воспроизводимыми обрывами после сборки и после сохранения конфигурации, затем проверка повторного запуска и сохранности карточек. Для работы на другом компьютере нужны исходники, lock-файлы и подходящие версии инструментов. Установленные зависимости и кэш одного компьютера могут потребовать пересоздания. Серверные секреты и данные переносятся отдельно.
